# 关键约束集中化与模块拆分计划

状态：2026-11-08 已实施并通过本机验收。下文保留原定阶段与验收条件；实际维护入口见 [CONSTRAINTS.md](CONSTRAINTS.md) 与 [ARCHITECTURE.md](ARCHITECTURE.md)。未改变合作游戏的自由属性接口，也未把外挂 GM 嵌入平台。

## 实施映射

- 约束目录：`CONSTRAINTS.md` 对身份、来源范围、持久化、事务、任务和接口记录权威数据与正反回归入口。
- 权限策略：`logstudio/ContentPolicy.h` 集中素材读取、共享导出、公开对象和缓存决策。保留 `AuthService`、`Visibility`、`StudioPolicy` 的现有边界。私密导出的素材读取与普通文件读取一致；私密配音和聊天插图通过迁移 `0061` / `0062` 记录来源范围；后台 ZIP 使用鉴权存储。
- 后端：`api/Api.cpp` 仅组合路由注册，`RouteSupport` 统一协议包装，六组业务路由各自注册。`ChatService` 的频道、角色、窗口和消息实现分别落在独立编译单元，跨职责查询片段在 `ChatQueries`。VN 保留服务生命周期入口，输入、文本提示、校验、确定性规划、续写、模型、分块恢复和素材调度各有模块。
- 外挂 GM：`loop.mjs` 保留构造、初始化与回合阶段顺序；`table/` 的调度、恢复、上下文、窗口、动作、绘图、规划、社交和玩家代理函数接受显式运行上下文。`api.mjs` 继续独占 HTTP 边界，已有幂等键、取消代际和持久状态格式保持兼容。
- 客户端：会话阶段与 socket 连接阶段显式命名，身份操作通过代际检查丢弃迟到响应并串行更新凭据；`SaveQueue` 区分编辑、写入和已保存版本，`ProjectLeases` 管理界面与任务持有。三端读取 `mobile/contracts/fixtures/session-errors.json` 与 `client-access.json`，核对会话错误、Studio 访问和缓存规则；只有服务 API 的 401 撤销本机会话。
- 持续集成：主 CI 按变更目录启用 Chromium/WebKit 浏览器流程；移动端工作流运行 Android 构建/单测/lint 和 iOS 核心/模拟器应用测试；相关 PR 可运行桌面原生检查。GM 单测隔离本机部署环境与自动 `.env` 加载。

部署管理员由用户名配置迁移到用户 ID 仍是将来需要设计的兼容迁移，不属于本次改变现有配置契约的内容。

## 产品边界

这是参与者自愿合作的 TRPG 平台。保留旧角色属性接口和自由修改角色数值的能力，不增加反作弊机制，不把购点编辑器的约束扩展为对所有数值写入入口的强制封锁。购点规则负责辅助玩家建卡；玩家与 GM 对实际玩法负责。

需要集中维护的约束是账号和权限身份、私密内容的可见范围、用户数据持久化、事务原子性、任务状态与恢复、接口兼容性。这些约束用于保护参与者的数据和操作预期。

第一版嵌入平台式 AI GM 在规划后已放弃，保留在 `AI_AGENTS_DESIGN.md` 作为历史资料。现有 GM Agent 是外挂式 Node.js 客户端，使用普通账户复用后端 HTTP 接口与 WebSocket 通知。后续拆分继续保持这一进程边界，不新增平台内 AI 座位或直接调用 C++ 服务的代理运行时。

## 第一阶段：建立约束目录和测试入口

为每条关键约束记录权威数据、负责服务、所有读写入口、失败时允许的状态，以及对应回归测试。先覆盖以下平行领域：

- 身份：管理员授权、用户名变更、注册、会话吊销、文件 token。未来评估把部署管理员配置迁移为不可变用户 ID，提供明确的兼容和撤权流程。
- 可见性：聊天、快照、回放、素材、缩略图、导出、公开对象存储、客户端缓存。衍生内容必须携带来源范围，只有明确发布操作能够扩大范围。
- 持久化：编辑中的版本、写盘中的版本、已落盘版本、失败重试、后台任务持有和退出提示。保存失败不能被当成成功，后写入的旧版本不能覆盖新内容。
- 事务：输入校验、状态转换、关联记录和通知。失败返回必须对应未提交状态，通知只能发生在提交后。
- 任务：领取、取消、重试、完成、进程恢复，以及删除来源对象时的收尾。每个转换都说明幂等键和资源归属。

验收条件：每条约束都能找到至少一个正向用例和一个失败/越权/并发用例；角色属性自由修改不列入违规项。

## 第二阶段：集中权限与来源范围

逐步从 API 路由和服务中收拢重复的身份、频道访问、来源范围与派生素材访问判断，形成少量有明确输入输出的策略函数。策略只做判断，不负责调用模型、写盘或发送通知。数据库查询继续带频道和主体条件，避免策略层变成唯一防线。

先迁移媒体元数据和文件访问，再迁移回放导出与发布，最后检查聊天衍生内容和缓存。为每个入口使用相同的身份/范围测试矩阵，包含 GM、角色所有者、同频道其他玩家、无频道权限者，以及权限被撤销后的访问。

验收条件：私密素材不会经列表、文件、公共 URL、导出或缓存扩大可见范围；已有公开发布与 GM 正常工作流仍可使用。迁移必须说明旧对象和 CDN 缓存的处置方法。

## 第三阶段：拆分后端应用流程

`api/Api.cpp` 按认证与管理、频道与聊天、角色与规则、Studio 与媒体分组注册路由，保留统一的鉴权、错误响应和工作池包装。路由层只处理协议转换，不承载业务状态转换。

`VnScriptService.cpp` 拆成输入与快照准备、模型编排、结构校验与归一化、分块恢复、素材需求调度几个内部模块。服务继续作为用例入口，统一事务和任务生命周期；纯数据转换优先提取为可独立测试的函数。

`ChatService` 按频道设置、角色资料、窗口成员与历史、消息操作逐步分离。规则切换保留一个事务入口；拆分不能把一个原子操作切成多个独立提交。

验收条件：每次只迁移一个职责，保持 HTTP 契约和数据库行为；相关数据库及 HTTP/WebSocket 测试通过后再迁移下一组。不做全仓库同时改名或无关格式化。

## 第四阶段：拆分外挂 GM Agent

把 `gm-agent/src/loop.mjs` 中的调度与取消、上下文组装、导演与规划、玩家代理决策、窗口迁移、平台动作执行分离。主循环保留阶段顺序和生命周期，具体能力通过显式依赖传入。

HTTP API 客户端负责认证续期、请求期限和取消传播；动作执行层负责幂等和结果核对；规划模块只产出结构化意图。玩家代理继续只读取自身可见的聊天和记录，不能复用 GM 的完整上下文。

验收条件：同一组固定输入在拆分前后产生相同的平台动作；取消、断线、重启恢复和多窗口权限测试通过。独立进程和现有 HTTP API 边界保持不变。

## 第五阶段：客户端状态和契约

把 Web/桌面中的会话恢复、账号切换、连接重试分别定义为明确状态，避免网络故障触发身份清除。项目编辑、保存队列和后台生成任务分别承担状态职责，通过版本和持有关系协作。

移动端继续使用各自的原生存储和界面，不为共享实现强行引入跨平台运行时。通过共同的接口示例、错误分类和权限场景验证 Web、iOS、Android 行为一致。

验收条件：覆盖断网、503、401、写盘失败、保存期间继续编辑、退出与重开、账号切换及旧请求迟到；私密缓存不能跨账号复用。

## 第六阶段：持续集成与文档

在 PR 中加入现有浏览器关键流程和移动端检查，按目录变化选择运行范围。桌面原生检查也应能在相关 PR 中执行。测试配置必须隔离开发者本机 `.env`，测试账户从受控夹具创建，不依赖公开接口抢占管理员名称。

每个拆分提交同时更新模块职责、依赖方向和运行方式；归档设计明确标记为历史，不再作为未完成路线图引用。优先记录稳定约束和维护入口，避免把易变化的测试计数当作长期文档事实。

验收条件：关键检查在合并前可见，失败能定位到对应层；架构文档与真实部署进程一致。完成上述阶段前不引入微服务拆分、不替换技术栈、不收紧合作游戏的自由数值接口。
